1. What is a socket?

Two programs want to talk. Maybe one is your browser and one is a server far away. They need a door to send and receive data. That door is called a socket.

Simple definition: A socket is one end of a two-way connection between two programs. Each program holds one end, like two people each holding one phone.

Letters vs. phone call

The normal web (HTTP) works like letters. You write a letter (request), the server answers (response), and then the conversation is over. If the server has news later, it cannot write to you first. You must ask again.

A socket stays open like a phone call. Both sides can talk at any time. That is why chat apps use sockets: a new message must reach you instantly, without you asking.

7. WebSocket

WebSocket is a protocol (a set of rules) that gives browsers a real two-way socket. It runs on top of TCP. The URL starts with ws:// (or wss:// when encrypted, like https).

It starts as normal HTTP

A WebSocket begins with a regular HTTP request that says "please upgrade me". If the server agrees, it replies 101 Switching Protocols. From then on, the same TCP connection is used for WebSocket data. This trick lets it pass through ordinary web servers and firewalls.

Frames: the small pieces

After the upgrade, data travels in small pieces called frames. A frame has a tiny header (2–14 bytes) and then your data. Compare that to HTTP, which repeats hundreds of bytes of headers on every request. That is why WebSocket is light and fast.

📝

Text frame

Your string, like JSON.

🧱

Binary frame

Raw bytes: images, audio, files.

🏓

Ping / Pong

"Are you alive?" "Yes!"

👋

Close frame

Polite goodbye with a reason code.

Plain WebSocket in code

// browser
const ws = new WebSocket("ws://localhost:5000");
ws.onopen    = () => ws.send("hello");
ws.onmessage = (e) => console.log(e.data);
ws.onclose   = () => console.log("closed");

What plain WebSocket does NOT give you: automatic reconnect, rooms, named events, "did the message arrive?" confirmation, or a fallback if WebSockets are blocked. You must build all that yourself, or use Socket.IO.

8. Socket.IO

Socket.IO is a library (for Node.js server and browser client) built on top of WebSocket. It adds the useful things we just said were missing. This is what our chat app uses.

Careful: Socket.IO is not the same as WebSocket. A plain WebSocket client cannot talk to a Socket.IO server, because Socket.IO wraps messages in its own format (see chapter 10).

Not just "a string". You say emit("message:send", data) and listen with on("message:send").

🔁

🪂

Fallback

If WebSocket is blocked, it starts with HTTP polling, then upgrades.

🏠

✅

"Did the server get it?" You can get a reply to a single emit.

9. Rooms & namespaces

A room is a named group of sockets on the server. A socket can join and leave rooms at any time. Sending to a room reaches only its members. Our app creates one room per chat room: room:<id>.

Namespaces

A namespace is a bigger divider: a separate "channel" on the same connection, with its own events and its own rooms. Example: /chat and /admin. Your old version of this app used io.of("/chat").

// one TCP connection, two namespaces

Easy rule: Namespace = different feature (chat, admin, game). Room = different group of users inside one feature.

10. Socket.IO packets & architecture

Socket.IO is two layers working together:

2
Socket.IOEvents, rooms, namespaces, acks. The part you use.
1
Engine.IOThe "engine": opens the connection, picks transport, upgrades, heartbeats, reconnect basics.
0
Transport: HTTP polling or WebSocketActual bytes on a TCP connection.

What happens when you call io()

  1. Open: client sends GET /socket.io/?EIO=4&transport=polling. Server answers with a session id (sid) and settings like pingInterval.
  2. Connect: client sends a "connect" packet (with your auth token). Server middleware checks it, then accepts.
  3. Upgrade: client opens a WebSocket on the side with the same sid, tests it with a ping/probe, then switches over and stops polling.
  4. Talk: events flow as small text packets.

Packet format

Every message is a short string. The first digit is the Engine.IO type, the second is the Socket.IO type, then comes the data (JSON).

Packet builder
Engine.IO digitMeaningSocket.IO digitMeaning
0 openHandshake (server → client)0 CONNECTJoin a namespace
1 closeClose transport1 DISCONNECTLeave a namespace
2 pingHeartbeat2 EVENTYour emit()
3 pongHeartbeat reply3 ACKReply to an event
4 messageCarries a Socket.IO packet4 CONNECT_ERRORRefused (e.g. "Unauthorized")
5 upgradeSwitch to WebSocket5 BINARY_EVENTEvent with files/bytes

So 42["chat","hello"] reads: Engine.IO 4 (message) → Socket.IO 2 (event) → data ["chat","hello"].

11. Middleware in depth

Middleware is a function that runs before your real code. It can look at the request, add information, say "OK, continue" (next()) or say "STOP" (next(new Error(...))). Think of airport security: you must pass every gate in order, and one "no" ends the trip.

Two kinds in Socket.IO

KindCodeRunsTypical use
Connection middlewareio.use((socket, next) => ...)Once, when a client connectsCheck JWT, load the user, check origin
Packet middlewaresocket.use(([event, ...args], next) => ...)Every event a client sendsRate limit, log, validate event names

You can also attach middleware to one namespace: io.of("/admin").use(...). Middleware runs in the order you write it.

Our real middleware

// server/src/socket.js
io.use(async (socket, next) => {
  try {
    const userId = verifyAccessToken(socket.handshake.auth.token);
    const user = await User.findById(userId);
    if (!user) throw new Error("no user");
    socket.data.user = user;   // handy storage for later code
    next();                    // ✅ let them in
  } catch {
    next(new Error("Unauthorized")); // ❌ refuse
  }
});

Packet middleware: check every event

io.on("connection", (socket) => {
  const allowed = ["room:open", "room:close", "message:send"];

  socket.use(([event], next) => {
    if (!allowed.includes(event)) return next(new Error("unknown event"));
    next();
  });

  // errors from packet middleware arrive here:
  socket.on("error", (err) => socket.emit("problem", err.message));
});

Tips

  • Order matters. Cheap checks first (rate limit by IP), expensive checks later (database).
  • Always call next() exactly once. Forget it and the client hangs forever. Call it twice and weird bugs appear.
  • Send safe messages. The error text goes to the client. Say "Unauthorized", not "JWT signature mismatch at line 42". You can add safe extra info with err.data = {code: 401}.
  • Store results in socket.data so later handlers don't repeat the work.
  • Middleware runs only on the first connect of each socket. Reconnecting runs it again (a new socket), which is good because the token is checked again.

Limit: io.use checks the user once. If their token expires or they log out later, the open socket stays alive. For strong safety, also disconnect sockets on logout or check the token time yourself with socket.use or a timer.

12. Sending binary data

Chat text is easy. But you may also want to send images, voice notes, files. These are binary data: raw bytes, not text. Good news: Socket.IO sends binary directly, no tricks needed.

What counts as binary?

WhereTypes you can pass to emit()
BrowserArrayBuffer, Blob, File, typed arrays (Uint8Array…)
Node.jsBuffer, ArrayBuffer, typed arrays
// client: send a picked file
const file = input.files[0];
socket.emit("upload", { name: file.name, type: file.type }, file);

// server: it arrives as a Buffer
socket.on("upload", (meta, buffer, ack) => {
  console.log(meta.name, buffer.length, "bytes");
  ack({ ok: true });
});

How it looks on the wire

JSON cannot hold raw bytes. So Socket.IO splits the message into pieces:

  1. A text frame with the packet and a placeholder where the bytes belong. It starts with 5 (BINARY_EVENT, see chapter 10), then how many binary parts follow.
  2. Then one binary frame for each part, sent right after.
// frame 1 (text):
51-["upload",{"name":"cat.png"},{"_placeholder":true,"num":0}]
// frame 2 (binary): the raw bytes of the file
89 50 4E 47 0D 0A 1A 0A ...

The receiving side glues them back, so your code just sees the object and the Buffer. Only binary-capable transports do this efficiently: WebSocket sends real binary frames. With HTTP polling the bytes are encoded as base64 text (bigger and slower).

How big is too big?
Drag the size. Socket.IO's server refuses a single message bigger than maxHttpBufferSize, default 1 MB (1,000,000 bytes).
💻Client
🖥️Serverlimit 1 MB

Rules of thumb

  • base64 makes data about 33% bigger (3 bytes become 4 characters). Prefer real binary.
  • Small things (voice note of a few seconds, a thumbnail, a drawing stroke): fine over the socket.
  • Big files (photos, videos): do not push them through chat sockets. Upload with a normal HTTP request (POST /upload) or straight to cloud storage using a pre-signed link, then send only the file's URL over the socket. Everyone else downloads it from there.
  • You can change the limit: new Server(httpServer, { maxHttpBufferSize: 5e6 }) (5 MB). Higher limits let attackers waste your memory, so keep it as low as you can.
  • Always check the file type and size on the server. Never trust the name or type the client claims.
  • Use socket.emit("x", data, {compress: true}) or volatile for data you can afford to lose (like live cursor positions).

13. CORS & connect_error

Part A: CORS in plain words

A browser has a safety rule called the same-origin policy: a page from site-A.com may not read answers from site-B.com. An origin is the trio protocol + domain + port. So http://localhost:5173 and http://localhost:5000 are different origins.

CORS (Cross-Origin Resource Sharing) is how a server says "I allow site-A.com to read my answers". It does this by sending headers like Access-Control-Allow-Origin.

How Socket.IO uses it

const io = new Server(httpServer, {
  cors: {
    origin: "https://chat.example.com", // ONLY your site, never "*" with login
    credentials: true,               // allow cookies
  },
});

Our trick: in development, Vite forwards /socket.io to port 5000. The browser thinks everything is on port 5173, so it is same-origin and CORS is not even needed. In production, put the website and API behind one domain for the same effect.

Big surprise: browsers apply CORS to HTTP requests (polling), but NOT to WebSocket connections. Any website can try to open a WebSocket to your server. So the cors option alone does not protect the WebSocket. You must check the Origin header yourself. This attack is called Cross-Site WebSocket Hijacking and it is dangerous when login is based on cookies.

Can an evil site connect?
Choose where the page comes from, how it connects, and whether the server checks Origin.
// Check the Origin yourself. This covers WebSocket too.
const io = new Server(httpServer, {
  cors: { origin: "https://chat.example.com" },
  allowRequest: (req, callback) => {
    const ok = req.headers.origin === "https://chat.example.com";
    callback(null, ok);   // second argument: true = allow, false = refuse
  },
});

Our app is safe from this attack anyway, because it logs in with a token sent in auth (which an evil page does not have), not with cookies. Still, adding the origin check is cheap extra safety.

Part B: connect_error and other client events

Connections fail. Wi-Fi drops, tokens expire, servers restart. Your client must listen for the problems:

The important flag: socket.active

  • socket.active === true: temporary problem. The library will retry by itself. Just show "reconnecting…".
  • socket.active === false: the server denied you (middleware error). It will not retry. You must fix the problem and call socket.connect() yourself.

socket.on("connect_error", async (err) => {
  if (socket.active) {
    showBanner("Reconnecting…");              // library retries by itself
    return;

  // denied by the server's middleware
  if (err.message === "Unauthorized") {

    else logout();                            // refresh failed: go to login
  }
});

socket.on("disconnect", (reason) => {
  if (reason === "io server disconnect") socket.connect(); // manual retry
});

Our current socket.js sends the freshest token on each reconnect, but it does not yet handle connect_error with "Unauthorized". The handler above is the missing piece.

14. TLS & wss://

Everything we sent so far travels as plain text. Anyone on the path (café Wi-Fi, a router, your internet provider) can read it and even change it. TLS (Transport Layer Security) wraps your connection in a locked tunnel. It is the "S" in HTTPS, and the "S" in wss://.

PlainSecureDefault port
http://https://80 → 443
ws://wss://80 → 443

Socket.IO over HTTPS automatically uses wss://. You do not change your Socket.IO code, only how the server is hosted.

What TLS gives you

🔒

Privacy

Data is scrambled. A spy sees nonsense.

🧾

Integrity

If someone changes even one bit on the way, it is detected.

🪪

Identity

A certificate proves you are talking to the real chat.example.com, not a fake.

The TLS handshake

It happens right after the TCP handshake (chapter 4), before any HTTP or WebSocket data. The big idea: use slow but clever math (public/private keys) just once to agree on a secret key, then use a fast shared key for all the chat data.

Certificates in one minute

  • A certificate says "this public key belongs to chat.example.com" and is signed by a Certificate Authority (CA) that your browser already trusts.
  • Free ones come from Let's Encrypt and renew automatically (every ~60–90 days).
  • Wrong domain, expired, or self-signed certificates make the browser show a red warning, and wss:// connections fail.
  • For local development you can use http://localhost without TLS.

Where to do TLS

Best practice: let a reverse proxy (nginx, Caddy, a cloud load balancer) handle the certificate and talk plain HTTP to Node on a private network. This is called TLS termination. It is simpler and faster than doing it inside Node.

# nginx: HTTPS in front, forwards Socket.IO to Node on port 5000
server {
  listen 443 ssl;
  server_name chat.example.com;
  ssl_certificate     /etc/letsencrypt/live/chat.example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/chat.example.com/privkey.pem;

  location /socket.io/ {
    proxy_pass http://127.0.0.1:5000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;     # needed for WebSocket
    proxy_set_header Connection "upgrade";      # needed for WebSocket
    proxy_set_header Host $host;
    proxy_read_timeout 120s;                    # longer than the ping interval
  }
}

Production checklist for our app

  • Serve the React site and the API on HTTPS only. Redirect port 80 to 443.
  • Set NODE_ENV=production. Our refresh-token cookie then gets the Secure flag, so the browser never sends it over plain HTTP.
  • Put app.set("trust proxy", 1) in Express, so rate limiting sees real client IPs behind the proxy.
  • Mixed content: an HTTPS page is not allowed to open a ws:// socket. The browser blocks it. Use wss:// (or a relative io() that follows the page).
  • Add the Strict-Transport-Security header (Helmet already does) so browsers refuse to use HTTP for your site.

15. Server options, one by one

When you create a Socket.IO server you can pass an options object. Think of it as the settings panel of your server. If you pass nothing, safe defaults are used and everything still works. You change an option only when you have a reason. This chapter explains every option that matters: what it is, its default, how to use it, and when you need it.

Three ways to create the server

// 1) Attach to an existing HTTP server (what our app does, shares the port with Express)
const httpServer = http.createServer(app);
const io = new Server(httpServer, { /* options */ });

// 2) Let Socket.IO make its own server on a port
const io = new Server(5000, { /* options */ });

// 3) No arguments, attach later
const io = new Server({ /* options */ });
io.attach(httpServer);

What our app uses today: only cors. Every other setting is a default. At the end of this chapter there is a builder that gives you a ready-made options object for your situation.

Group 1: Where and how clients connect

pathdefault: "/socket.io"

What it is: the URL path where Socket.IO listens. Every handshake and polling request goes to https://yourhost/socket.io/?EIO=4&... (you saw this URL at the start of our journey).

// server
new Server(httpServer, { path: "/chat-socket" });
// client: must match exactly
io({ path: "/chat-socket" });

Use cases

  • One domain hosts two Socket.IO apps (for example /support-socket and /game-socket).
  • A reverse proxy only forwards certain paths (the nginx location must match the path).
  • You want to hide that you use Socket.IO (minor, not real security).

Watch out: if client and server paths differ, you get 404 errors and connect_error forever. The Vite proxy in our vite.config.js also forwards /socket.io, so change it there too.

serveClientdefault: true

What it is: when true, the server also hands out the browser library at /socket.io/socket.io.js, so a plain HTML page can use <script src="/socket.io/socket.io.js">.

new Server(httpServer, { serveClient: false });

Use cases

  • Set false when your frontend is built with a bundler (React + Vite, like ours) and imports socket.io-client itself. Less surface and nothing extra to serve.
  • Keep true for quick demos with a simple HTML file and no build step.
addTrailingSlashdefault: true

What it is: whether the path is /socket.io/ (with a final slash) or /socket.io. Only matters for picky proxies.

new Server(httpServer, { addTrailingSlash: false });

Use case: a proxy or load balancer rule matches /socket.io exactly and rejects the slash version. Most people never touch this.

Group 2: Transports (how the bytes travel)

transportsdefault: ["polling", "websocket"]

What it is: the list of ways a client may connect. By default a client starts with HTTP polling (works almost everywhere) and then upgrades to WebSocket.

new Server(httpServer, { transports: ["websocket"] });
// the client must agree, otherwise it starts with polling and is refused:
io({ transports: ["websocket"] });

Use cases

  • Default (both): best for public websites. Works behind strict company firewalls, then gets the speed of WebSocket.
  • ["websocket"] only: faster first connection (no polling round-trips), and much simpler with many servers, because without polling you don't need sticky sessions (chapter 18). Great for apps whose users are on normal networks, like mobile apps.
  • ["polling"] only: very rare, for environments that block WebSocket completely.
  • An experimental "webtransport" exists too (works over HTTP/3), for advanced use.

Watch out: WebSocket-only fails on networks that block WebSocket (some corporate proxies). Decide based on who your users are.

Group 3: Heartbeat and timeouts

pingInterval and pingTimeoutdefaults: 25000 ms and 20000 ms

What they are: the heartbeat from chapter 17. Every pingInterval the server sends a ping. The client must answer with pong within pingTimeout. If not, the socket is declared dead.

So a silently dead connection is noticed in about pingInterval + pingTimeout (45 seconds by default).

new Server(httpServer, {
  pingInterval: 10000,  // ping every 10 s
  pingTimeout:  5000,   // wait 5 s for pong
});

The client reads these two numbers from the handshake, so you only set them on the server.

Use cases

  • Shorter values (10 s + 5 s): games, live auctions, presence ("online now" dots) where you must notice a disconnect fast. Cost: more tiny packets and more battery use.
  • Longer values: huge numbers of idle clients where you want less traffic, or mobile apps that sleep in the background and would otherwise be dropped too often.
  • Behind a proxy: the proxy's idle timeout (nginx proxy_read_timeout, default 60 s) must be longer than pingInterval, or the proxy cuts quiet connections.

connectTimeoutdefault: 45000 (ms)

What it is: after the transport is open, the client must finish joining a namespace (this is when your io.use middleware runs). If that does not happen within this time, the server drops the connection.

new Server(httpServer, { connectTimeout: 10000 });

Use case: protect the server from clients that open a connection and then sit there doing nothing (a cheap way to waste your resources). Lower it to 5–10 s. If your auth middleware calls a slow database, don't set it too low.

Group 4: Message size and compression

maxHttpBufferSizedefault: 1e6 (1 MB)

What it is: the biggest single message the server accepts, in bytes. A bigger message makes the server close that connection (chapter 12).

new Server(httpServer, { maxHttpBufferSize: 1e5 });  // 100 KB

Use cases

  • Lower it for text chat. Our messages max 1000 characters, so 100 KB is generous. A small limit stops attackers from making you buffer huge messages.
  • Raise it (for example 5e6) only when you truly send small files or images through the socket. For big files use HTTP uploads.
perMessageDeflatedefault: false (off)

What it is: compresses every WebSocket message (zlib, like making a zip). Smaller on the wire, but it costs CPU and memory for every connection, which can hurt badly with many users.

new Server(httpServer, {
  perMessageDeflate: { threshold: 1024 },  // only compress messages over 1 KB
});

Use cases: large text payloads (big JSON lists) and customers on slow or expensive mobile data. Don't enable for tiny chat messages: compressing 40 bytes saves nothing.

You can also decide per message: socket.compress(false).emit(...).

httpCompressiondefault: true

What it is: same idea as above, but for HTTP polling responses. On by default, and only compresses larger responses.

new Server(httpServer, { httpCompression: { threshold: 2048 } });

Use case: usually leave it. Turn it off (false) if CPU is tight and most users are on WebSocket anyway.

Group 5: Origin, cookies and security

corsdefault: none (no CORS headers)

What it is: tells browsers which other websites may use your server through HTTP polling (chapter 13). It takes the same settings as the Express cors package.

new Server(httpServer, {
  cors: {
    origin: ["https://chat.example.com", "https://admin.example.com"], // allowed sites
    methods: ["GET", "POST"],
    credentials: true,                  // allow cookies
  },
});

Use cases

  • Website and server on different domains or ports (app.example.com and api.example.com).
  • Not needed when both are on the same origin (our Vite proxy setup).

Never use origin: "*" together with credentials: true or on a logged-in app. And remember: cors does not stop WebSocket connections. Pair it with allowRequest.

allowRequestdefault: none (everyone is allowed)

What it is: a function that runs on every handshake, before anything else, and can refuse. It receives the raw HTTP request, so you can read headers, cookies and the IP address.

new Server(httpServer, {
  allowRequest: (req, callback) => {
    const okOrigin = req.headers.origin === "https://chat.example.com";
    callback(null, okOrigin);   // (error, allowed?)  false = refused with HTTP 403
  },
});

Use cases

  • Check the Origin header, which covers WebSocket too (stops cross-site hijacking).
  • Block bad IPs or a country list before spending any more resources.
  • Cheap early auth by checking an API key in a header.

Difference from io.use: allowRequest runs at the very first HTTP request and sees raw HTTP. io.use runs after the connection exists and sees the Socket.IO handshake (including auth). Use allowRequest for network-level checks and io.use for login.

cookiedefault: false (no cookie)

What it is: makes the server set a small cookie (named io by default) holding the session id. Some load balancers use it to send the same client to the same server (sticky sessions, chapter 18).

new Server(httpServer, {
  cookie: { name: "chat_sid", httpOnly: true, sameSite: "strict", secure: true },
});

Use case: several servers behind a load balancer with polling enabled. If you use WebSocket-only, or the balancer sticks clients by IP, you don't need it. If you do turn it on, add the safe flags shown above.

Group 6: Scaling and recovery

adapterdefault: in-memory adapter

What it is: the part that knows who is in which room and how to broadcast. The default lives in one server's memory. To make several servers act as one, replace it (chapter 18).

const { createAdapter } = require("@socket.io/redis-adapter");
new Server(httpServer, { adapter: createAdapter(pubClient, subClient) });

Use cases: two or more Node processes (many servers, or Node's cluster mode). A single server needs nothing.

connectionStateRecoverydefault: off

What it is: after a short disconnect (tunnel, Wi-Fi switch), the server keeps the socket's id, its rooms, and the events it missed, and gives them back when the client reconnects. Without it, the new connection is a brand-new socket with no rooms (chapter 17).

// server
new Server(httpServer, {
  connectionStateRecovery: {
    maxDisconnectionDuration: 2 * 60 * 1000,  // remember for 2 minutes
    skipMiddlewares: true,                     // don't re-run auth middleware on recovery
  },
});

// client: find out if recovery worked
socket.on("connect", () => {
  if (socket.recovered) {
    // same id, rooms and missed events are back: nothing else to do
  } else {
    // new session: join rooms again and reload data
  }
});

Use cases: chat and live feeds where missing a few messages is annoying. In our app it would replace some of the manual re-join logic, though we'd still keep the history reload as a fallback because recovery only covers short gaps.

Watch out: events are kept in memory, so it uses RAM. Recovery fails after a server restart or after the time limit. With many servers you need an adapter that supports it (such as the Redis Streams adapter).

cleanupEmptyChildNamespacesdefault: false

What it is: only for dynamic namespaces (io.of(/^\/workspace-\d+$/)). When true, a namespace created on the fly is deleted once its last client leaves, freeing memory.

new Server(httpServer, { cleanupEmptyChildNamespaces: true });

Use case: a multi-tenant app creating a namespace per company or per workspace. Not needed if you use fixed namespaces or only rooms (like us).

Group 7: Compatibility and wire format

allowEIO3default: false

What it is: lets very old clients (Socket.IO v2, Engine.IO protocol 3) connect to a new v4 server.

Use case: you upgraded the server but old mobile apps still in users' hands use v2. Turn on temporarily while they update, then remove it. Old versions have known weaknesses.

What it is: how packets are turned into bytes and back (chapters 10 and 12). You can plug in another one, such as MessagePack, which is smaller and faster than JSON for some data.

const parser = require("socket.io-msgpack-parser");

16. Server instance vs socket instance

  
This is the most confusing part for beginners, because the word "socket" is used in many places. Let's give every object a clear name. There are really three different objects:


  

    
🏢
1. Server instance
Called io in our code. One per server program. It is the whole building: it knows every client, every room, every namespace.

    
🧑‍💼
2. Socket instance (server side)
Called socket inside io.on("connection", (socket) => ...). One per connected client. It is that one person's phone line.

    
📱
3. Socket instance (client side)
Called socket in the browser: const socket = io(). It is the other end of the same phone line.

  


  
Easy picture: A call centre. The call centre building is io (one). Every customer who calls gets a phone line with the agent: the agent's side is the server-side socket, the customer's side is the client-side socket. The building can announce something over the loudspeaker to everyone (io.emit), or an agent can talk on just one line (socket.emit).

// CLIENT (browser)

The socket instance on the server in detail

  
Socket.IO makes it for you the moment a client connects, and hands it to your "connection" callback. Everything about one user lives on this object.



// Properties: facts about this one client
socket.id                       // "k3Jx9Zq1AbCdEfGh": unique, changes on every reconnect

Every socket has its own private room

  
When a socket connects, it is automatically placed in a room named its own id. That gives you a private channel:


// send a private message to one specific socket from anywhere
io.to(otherSocketId).emit("private", "psst");


  
One person can have many sockets

  
One user can have many sockets: a laptop tab, a second tab, a phone. Each gets its own socket.id. So "send to this person" needs a room named after the user, not the socket:


io.on("connection", (socket) => {
  socket.join(`user:${socket.data.user.id}`);   // all tabs of this user share this room
});

// anywhere later: reaches every tab and device of that user
io.to(`user:${userId}`).emit("notification", { text: "New invite" });

// logout everywhere / ban:
io.in(`user:${userId}`).disconnectSockets();

  
That last line is exactly the fix for the gap we found earlier: sockets that stay open after logout. Join a user:ID room at connect, and on logout call disconnectSockets() for that room.

Behind the client socket there is a Manager (socket.io). It owns the one real connection to the server and handles reconnection.   • Mixing up io.emit and socket.emit. io.emit = everyone. socket.emit = just that one client. A chat message sent with socket.emit would reach only the sender!
    • 
    
  • Registering io.on inside io.on("connection"). That adds a new listener for every client and leaks memory. Per-client things go on socket. Global things go on io, once.
    • 
    
  • Adding socket.on(...) outside the connection callback. There is no socket yet. Handlers must be registered inside it.
    • 
    
  • Treating socket.id as a user id. It changes on every reconnect, and one user can have many. Store the real user in socket.data.user and use a user:ID room.
    • 
    
  • Keeping state in global variables (let onlineUsers = []). It breaks with many servers. Prefer socket.data, rooms, fetchSockets() or a database.
    • 
    
  • Forgetting that rooms vanish when the socket does. A reconnect makes a new socket with no rooms. Join again, or use connection state recovery (chapter 15).
    •

17. Heartbeat & reconnect

  
A TCP connection can look open even when the other side is dead (laptop closed, Wi-Fi gone). Nobody is told. So Socket.IO uses a heartbeat: the server sends a ping every ~25 seconds. The client must answer with pong. If the answer does not come in time (~20 seconds), the connection is declared dead.

  
When the client notices it is disconnected, it reconnects by itself. It waits a little, tries again, and waits longer each time (this is called exponential backoff), plus a random bit so thousands of clients do not all knock at the same moment.

20. How sockets get hacked, and how to stop it

  
Chapter 19 gave a short table. Here we go deep. Each tab below is one real kind of attack. For each one you get: a simple story, how it works step by step, an animation you can switch between "no defence" and "defence ON", bad code vs good code, and whether our chat app is safe.


  
Why learn this? You can only defend what you understand. This is for building safe apps and protecting your own systems. Never test attacks on servers you do not own or have permission to test.


  
One idea explains almost every attack: a socket is a long-open door, and everything that comes through it is typed by a stranger. The browser is controlled by the user, so a hacker can send anything they want, in any shape, at any speed, with any claimed identity. So the server must never trust the client. It must check who is talking, what they are allowed to do, and whether the data is the right shape.

io("http://chat.example.com");   // ws:// underneath

      
✅ Strong
// client: https page + same-origin or wss
io("https://chat.example.com"); // wss:// underneath
// server: HTTPS (via nginx), HSTS, secure cookies

    

    
Defences

    
    
      
  • Always TLS in production (https:// and wss://). See chapter 14.
    • 
      
  • Redirect HTTP to HTTPS and send the HSTS header (Helmet does) so browsers never fall back.
    • 
      
  • Set Secure on cookies so they never travel over plain HTTP.
    • 
      
  • Never put tokens in URLs (?token=...): URLs end up in logs and history.
    • 
    

    
⚠️ Our app: works over plain HTTP in development (fine for localhost). For real use you must host it behind HTTPS. Production mode already turns on the Secure cookie flag.

  


  
  

    
🎭 Cross-site WebSocket hijacking

    
Story: You are logged in to your chat in one tab. In another tab you open a bad website. That bad page secretly dials your chat server using your browser, and the browser helpfully attaches your login cookie. The server thinks it is you.

    
How it works:

    
    
      
  1. Login is stored in a cookie. Browsers attach cookies automatically to requests for that site, even if the request was started by another site.
    2. 
      
  2. Browsers do not apply CORS to WebSocket connections (chapter 13).
    3. 
      
  3. So evil.com runs new WebSocket("wss://chat.example.com") and the server accepts it as the logged-in victim. The attacker's page can now read the victim's messages and send messages as them.
    4. 
    

    

    

      
❌ Weak: trusts the cookie, no origin check
io.use((socket, next) => {
  const user = userFromCookie(socket.request);
  next();   // any website can reach this
});

      
✅ Strong
new Server(httpServer, {
  allowRequest: (req, cb) =>
    cb(null, req.headers.origin === ALLOWED),
});
// and authenticate with a token in `auth`,
// not with a cookie the browser sends by itself

    

    
Defences

    
    
      
  • Check the Origin header with allowRequest (chapter 15).
    • 
      
  • Use a token sent in auth. A foreign page cannot read your token, so it cannot connect.
    • 
      
  • If you must use cookies, set SameSite=Strict (or Lax).
    • 
    

    
✅ Our app is protected because it logs in sockets with a JWT in auth, which evil.com cannot get. ⚠️ To be extra safe we should still add the allowRequest origin check.

  


  
  

    
🎫 Token theft, forgery and stale sessions

    
Story: Your wristband gets you into the party. A thief can steal it, copy it, or make a fake one that looks real. And if the club never checks wristbands again after the door, an expelled guest stays inside.

    
How it works:

    
    
      
  • Guessing the secret: a weak JWT_SECRET like "secret123" can be cracked offline, then fake tokens can be signed for any user.
    • 
      
  • Algorithm trick: some libraries accept a token that says "alg: none" (no signature at all) if you do not pin the algorithm.
    • 
      
  • Stealing: tokens leaked through URLs, logs, XSS, or localStorage stolen by a script.
    • 
      
  • Stale sessions: a socket is only checked once at connect. After logout or token expiry the open socket keeps working.
    • 
    

    

    

      
❌ Weak
jwt.verify(token, "secret123");        // weak secret
jwt.verify(token, secret);               // no algorithms list
io(url + "?token=" + token);               // token in URL

      
✅ Strong
jwt.verify(token, secret, {
  algorithms: ["HS256"],     // pinned
});                              // secret: 48 random bytes
io({ auth: { token } });        // not in the URL
// short life (15 min) + kick on logout:
io.in(`user:${id}`).disconnectSockets();

    

    
Defences

    
    
      
  • Long random secret (we refuse to start under 32 characters). Keep it in .env, never in git.
    • 
      
  • Pin the algorithm when verifying.
    • 
      
  • Short-lived access tokens and rotated refresh tokens (our design).
    • 
      
  • Keep tokens in memory, not in localStorage. Send via auth, never in the URL.
    • 
      
  • Kick sockets on logout, ban, or password change, and re-check on a timer.
    • 
    

    
✅ Done: pinned HS256, 32+ char secret enforced, 15 min tokens, token in auth, rotation. ❌ Missing: an already-open socket is not re-checked or disconnected after logout or token expiry.

  


  
  

    
🚪 Getting into rooms you should not (broken authorization)

    
Story: The hotel checks your key at the front door, but then every room door is unlocked. Once inside, you can walk into anyone's room by just guessing the number.

    
How it works:

    
    
      
  1. The attacker has a normal account (they are authenticated).
    2. 
      
  2. They emit room:open with the id of a private room they got from a link, a log, or by guessing.
    3. 
      
  3. If the server only checks "are you logged in?" and not "are you a member?", they receive every message of that room. This is called IDOR (insecure direct object reference).
    4. 
    

    

    

      
❌ Weak
socket.on("room:open", (roomId) => {
  socket.join(`room:${roomId}`);  // no check!
});

      
✅ Strong (what we do)
socket.on("room:open", async (roomId, ack) => {
  const room = await Room.findOne({
    _id: roomId, members: user._id,  // member?
  });
  if (!room) return ack({ error: "Not a member" });
  socket.join(`room:${room._id}`);
});

    

    
Defences

    
    
      
  • Authorize every action, not just the connection: join, read, send, delete.
    • 
      
  • Ask the database at the time of the action (people leave or get banned).
    • 
      
  • Do not rely on hard-to-guess ids as security. Treat ids as public.
    • 
      
  • Apply the same rules to HTTP routes and socket events. Two doors, same lock.
    • 
    

    
✅ Our app is protected: room:open, message:send and GET /messages all check membership, and our test proves a non-member is refused.

  


  
  

    
🥸 Identity spoofing

    
Story: A letter says "From: the Bank Manager". The envelope is just handwriting, so anyone can write it. You must check the postmark, not the claim.

    
How it works:

    
    
      
  1. The client sends { sender: "admin", text: "Send me money" }.
    2. 
      
  2. A careless server copies sender from the payload into the message and broadcasts it.
    3. 
      
  3. Everyone sees a message "from admin" that really came from the attacker.
    4. 
    

    

    

      
❌ Weak
socket.on("message:send", ({ sender, text }) => {
  io.emit("message:new", { sender, text });
});

      
✅ Strong (what we do)
socket.on("message:send", ({ roomId, text }) => {
  // identity comes from the verified token
  const sender = socket.data.user;
  Message.create({ room: roomId, sender: sender._id, text });
});

    

    
Defences

    
    
      
  • Identity only from the server's own record (socket.data.user), never from event data.
    • 
      
  • The same goes for roles ("isAdmin"), prices, owners, and timestamps.
    • 
      
  • Ignore or reject unknown fields in payloads.
    • 
    

    
✅ Our app is protected: the sender is always socket.data.user, and the payload schema only allows roomId and text.

  


  
  

    
💉 Injection: XSS and NoSQL

    
Story: You ask someone to read your note aloud. The note says "now stand up and give me your wallet". A careless reader does exactly what the note says. Data must stay data, never become instructions.


    
A) XSS (script in a chat message)

    
    
      
  1. The attacker sends the message <img src=x onerror="steal()">.
    2. 
      
  2. Your page puts it into the screen with innerHTML. The browser treats it as real HTML and runs the script in every viewer's browser.
    3. 
      
  3. The script can read the page, steal tokens kept in localStorage, and act as the victim.
    4. 
    

    
B) NoSQL injection (object instead of string)

    
    
      
  1. The server expects roomId to be a string. The attacker sends an object: { "$ne": null }.
    2. 
      
  2. The server puts it straight into a MongoDB query. MongoDB reads $ne as an operator ("not equal null") and matches far more than intended.
    3. 
    

    

    

      
❌ Weak
el.innerHTML = msg.text;               // XSS
Room.findOne({ _id: roomId });         // roomId could be an object

      
✅ Strong
// React: {msg.text} is escaped automatically
const roomIdSchema = z.string().regex(/^[0-9a-f]{24}$/i);
const parsed = roomIdSchema.safeParse(roomId);
if (!parsed.success) return ack({ error: "Invalid room" });

    

    
Defences

    
    
      
  • Validate every payload with a schema (zod): exact types, lengths, patterns. Reject everything else.
    • 
      
  • Escape on output. Use textContent or a framework that escapes (React does). Never innerHTML with user text.
    • 
      
  • Add a Content-Security-Policy header (Helmet) to limit what scripts can run.
    • 
      
  • Do not keep tokens in localStorage, so an XSS cannot steal them.
    • 
    

    
✅ Our app now: React escapes messages, REST bodies use zod, and socket payloads are now validated too. Our own testing found that room:open used to accept {"$ne":null}. That is fixed and covered by a test.

  


  
  

    
🌊 Floods and denial of service (DoS)

    
Story: A crowd of people ring your doorbell nonstop. You cannot answer the real visitors because the bell never stops.

    
How it works: sockets stay open and cost memory, so there are many ways to overload them:

    
    
      
  • Message flood: one client sends thousands of events per second.
    • 
      
  • Connection flood: a bot opens tens of thousands of sockets.
    • 
      
  • Idle hoarding: sockets that connect and then do nothing, just to take up slots.
    • 
      
  • Huge payloads: giant messages that fill memory.
    • 
      
  • Expensive events: an event that causes a heavy database query, repeated again and again.
    • 
    

    

    

      
❌ Weak
new Server(httpServer);          // defaults: 1 MB messages, 45 s to connect
socket.on("search", async (q) => {
  await HeavyQuery(q);          // no limit
});

      
✅ Strong
new Server(httpServer, {
  maxHttpBufferSize: 1e5,   // 100 KB
  connectTimeout: 10000,    // finish connecting fast
});
// per-socket limit (we do this: 15 msgs / 10 s)
// per-IP connection cap at nginx: limit_conn

    

    
Defences

    
    
      
  • Rate limit events per socket and per user. Slow or disconnect abusers.
    • 
      
  • Limit connections per IP and overall (nginx limit_conn, a cloud WAF, or a firewall).
    • 
      
  • Lower maxHttpBufferSize and connectTimeout (chapter 15).
    • 
      
  • Require authentication early, so anonymous bots can do little.
    • 
      
  • Keep event handlers cheap: pagination limits, indexes, timeouts.
    • 
      
  • Put a CDN or load balancer in front, and set up monitoring and alerts for connection counts.
    • 
    

    
✅ Done: 15 messages / 10 s per socket, 1000-character limit, login required to connect. ⚠️ Not yet: per-IP connection limit, lower maxHttpBufferSize, shorter connectTimeout. The Express rate limiter covers /api but not /socket.io.

  


  
  

    
💥 Malformed payloads that crash the server

    
Story: A vending machine expects coins. Someone feeds it a banana and the whole machine jams for everybody.

    
How it works:

    
    
      
  1. Your handler assumes the data has a shape: ({ roomId, text }).
    2. 
      
  2. The attacker emits null, a number, a huge array, or leaves out the callback.
    3. 
      
  3. The code throws an error that nobody catches. In Node.js an uncaught exception kills the whole process, which disconnects every user.
    4. 
    

    
This really happened in our app. While writing this chapter I tested our server: socket.emit("message:send", null) from any logged-in user crashed it with Cannot destructure property 'roomId' of null. I fixed it by validating every payload with a schema. A regression test now covers it.

    

    

      
❌ Weak (our old code)
socket.on("message:send", async ({ roomId, text } = {}, ack) => {
  // null → TypeError → server process dies
  ack?.({ ok: true });  // ack not a function → TypeError
});

      
✅ Strong (our code now)
const replyTo = (ack) =>
  typeof ack === "function" ? ack : () => {};

socket.on("message:send", async (payload, ack) => {
  const reply = replyTo(ack);
  const parsed = sendSchema.safeParse(payload);
  if (!parsed.success) return reply({ error: "Bad message" });
  // ...use parsed.data only
});

    

    
Defences

    
    
      
  • Never destructure the raw payload. Parse it with a schema first.
    • 
      
  • Wrap handlers in try/catch, and treat ack as optional and untrusted.
    • 
      
  • Limit sizes of strings and arrays inside the schema.
    • 
      
  • Handle "error" events, and use a process manager (pm2, systemd, Docker restart) so a crash recovers quickly. This is a safety net, not a fix.
    • 
      
  • Fuzz your events in tests: send null, [], {}, a 1 MB string, wrong types.
    • 
    

    
✅ Fixed in our app (server/src/socket.js) and protected by the test "sockets survive malformed payloads".

  


  
  

    
🫗 Data leaks

    
Story: You ask the waiter for the menu and he hands you the restaurant's entire accounting book. Nothing was "hacked"; the server simply said too much.

    
How it works:

    
    
      
  • The server broadcasts a whole database object, with email, password hash, tokens, internal ids, because that was easier than picking fields.
    • 
      
  • Every client receives it. Anyone can open DevTools, see the WebSocket frames, and read all of it.
    • 
      
  • Detailed error messages ("JWT signature mismatch", stack traces) teach attackers how the server works.
    • 
      
  • Private data sent to a room that is wider than it should be.
    • 
    

    

    

      
❌ Weak
io.to(room).emit("message:new", {
  ...message,
  sender: user,    // contains email, hash...
});
ack({ error: err.stack });

      
✅ Strong (what we do)
// only the fields the client needs
io.to(room).emit("message:new", message.toPublic(user));
// → sender: { id, username }
ack({ error: "Could not send message" });  // generic
// passwordHash is select:false and never loaded

    

    
Defences

    
    
      
  • Send only what is needed (a "public view" function like our toPublic()).
    • 
      
  • Keep secrets out of normal queries (select: false).
    • 
      
  • Generic error messages to clients. Log details on the server.
    • 
      
  • Think carefully about who is in each room before emitting. Use per-user rooms for private data.
    • 
      
  • Disable debug tools (like the Socket.IO Admin UI) in production or protect them with strong auth.
    • 
    

    
✅ Our app is protected: messages use toPublic() (only id + username), passwordHash is never selected, and errors are generic.
